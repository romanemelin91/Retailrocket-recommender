# Рекомендательная система для интернет-магазина 

## 1. Постановка задачи
Показать пользователю 3 товара, которые он купит в ближайшие 14 дней. Цель - рост продаж от рекомендаций.
Метрика: Precision@3 (дополнительно Recall@3 и HitRate@3), усреднение по покупателям периода.
Влияние на оборот НЕ измерялось (оффлайн-метрика); эффект подтверждается только A/B-тестом.

## 2. Данные
- `events.csv`: timestamp (мс), visitorid, event ∈ {view, addtocart, transaction}, itemid, transactionid. 2 756 101 строка, период 2015-05-03 … 2015-09-18, 1 407 580 пользователей.
- Структура событий: 97% просмотры, ~2,5% добавления в корзину, <1% покупки; у 71% пользователей одно событие, у 94% - меньше пяти.
- `category_tree.csv`: 1669 категорий, 25 корневых. `item_properties_part1/2.csv`: 20 275 902 записи, 1104 свойства, осмысленны только `categoryid` и `available` (остальные захешированы).
- Использование: category_tree и item_properties изучены; в итоговую модель не включены.

## 3. Преобразования
- Удалено 460 полных дублей (2 756 101 → 2 755 641 строка).
- timestamp переведён в дату (UTC).
- Пропуски `transactionid` (только у покупок есть значение) и `parentid` (у корневых категорий) ожидаемы и не удалялись.
- Из `item_properties` оставлены только свойства `categoryid` и `available`.

## 4. Временная валидация
Разбиение по времени: train - до 2015-08-21 02:59:47, validation - с 2015-08-21 до 2015-09-04 (14 дней), test - последние 14 дней (2015-09-04 … 2015-09-18). Признаки считаются только по истории до границы, цели - покупки в следующие 14 дней.
Для XGBoost/FM окна сдвинуты на 14 дней: обучение - признаки до train_end−14 дней, метки в следующих 14 днях.
Защита от утечки: `assert` в функции `build_tables`, проверки разбиения (выборки не пересекаются и покрывают все события) и блок проверок признаков (счётчики, окна, диапазоны, отсутствие NaN/inf).
Финальная модель перед test обучается на train + validation; test считается один раз, после выбора модели.

## 5. Признаки
Итоговая модель (персональная история) использует только веса событий 1/5/15. Признаки ниже использовались в экспериментах XGBoost и FM (функция `build_tables`):

| Группа | Признаки | Как считается |
|---|---|---|
| Пара пользователь–товар | pair_view / addtocart / transaction, total_interactions, interaction_score, recency_days, has_pair_history | счётчики событий, взвешенная сумма (1/5/15), дни с последнего события |
| Пользователь | user_view/addtocart/transaction, user_unique_items, user_conversion, user_recency_days, user_views_7d/30d, has_user_history | счётчики, сглаженная конверсия, давность, активность за окна |
| Товар | item_view/addtocart/transaction, item_unique_users, item_conversion, item_cart_rate, item_recency_days, item_transactions_7d/30d | то же для товара |

Конверсия сглаживается: (n + α·prior) / (d + α), α = 5, prior - средняя по магазину.
Признаки быстрого листания и длительности просмотра исследовались, но в итоговые таблицы не включены: они касаются около 1% просмотров.

## 6. Эксперименты (validation, 1131 покупатель)
| Модель | Precision@3 [95% ДИ] | Recall@3 | HitRate@3 |
|---|---|---|---|
| **Персональная история 1/5/15** | **0,0242 [0,0189; 0,0298]** | 0,0557 | 0,0672 |
| FM | 0,0224 [0,0171; 0,0280] | 0,0553 | 0,0619 |
| Гибрид: история + XGBoost | 0,0224 [0,0171; 0,0280] | 0,0544 | 0,0619 |
| XGBoost | 0,0215 [0,0165; 0,0265] | 0,0549 | 0,0628 |
| Популярность | 0,0071 [0,0044; 0,0100] | 0,0114 | 0,0203 |

Другие проверенные варианты (Precision@3): популярность за 7 дней 0,0068; веса 1/1/1 - 0,0233, 1/3/10 - 0,0242; затухание 7/30/60 дней - 0,0242 / 0,0239 / 0,0242; ItemKNN - 0,0077; ALS (лучшая конфигурация) - 0,0127.
Фильтрация на "справочнике истории" (пороги 5 событий / 5 покупок): только пользователи 0,0171, только товары 0,0133, оба 0,0115 - хуже, так как фильтр убирает историю у большинства пользователей. Фильтрация обучающей выборки XGBoost не исследовалась.

**Выводы.**
- Все модели надёжно лучше популярности (интервалы разности не содержат 0).
- Различия между персональной историей, XGBoost и FM в пределах шума (≈82 попадания на validation), поэтому преимущество сложных моделей не доказано.
- Для новых покупателей (83%) XGBoost/FM/гибрид (0,0032-0,0036) не лучше популярности (0,0057).
- Выбрана модель по истории: не хуже остальных, проще и компактнее в сервисе.

## 7. Итог на test (1057 покупателей, модель обучена на train + validation)
- Precision@3 = 0,0290 (95% доверительный интервал [0,0230; 0,0350]) против 0,0158 у популярности ([0,0117; 0,0202]); 92 попадания против 50 из 3171 рекомендации.
- Прирост +0,0132 (+1,3 п.п.; 95% доверительный интервал [0,0085; 0,0183]), относительно +84%; разность значима.
- Известные покупатели (199): 0,0938; новые (858, ≈81%): 0,0140 - им рекомендуются популярные товары.
- Рост оборота не измерялся; 84% относится к Precision@3.

## 8. API и запуск сервиса
Сервис на FastAPI читает артефакты из `artifacts/` (`user_top.json`, `popular.json`, `metrics.json`), которые создаёт артефакты, API и веб-сервис. Сервисная модель обучена на всех данных до конца датасета; метрики в `/metrics` получены на test.

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/health` | `{"status":"ok","users_in_model":...,"popular_items":20}`; 503, если артефакты не загружены |
| GET | `/metrics` | содержимое `artifacts/metrics.json` |
| GET | `/recommend/{user_id}` | `{"user_id":172,"items":[...3 товара...],"source":"personal"}` |

- Известный пользователь: `source = personal`, три товара по его истории (если их меньше трёх, остаток добирается популярными).
- Неизвестный пользователь: `source = popular`, три самых популярных товара.
- Некорректный `user_id` (не число, дробное, отрицательное): ответ 422, сервис не падает.
- Интерактивная документация: `http://localhost:8000/docs`.

### Запуск без Docker (проверено: 8 тестов пройдено, запросы возвращают ожидаемые ответы)
```powershell
python -m pip install fastapi "uvicorn[standard]" pytest httpx
python -m pytest -q tests/test_service.py          # ожидаемо: 8 passed
python -m uvicorn service.app:app --port 8000      # затем http://localhost:8000/docs
```
Остановка сервиса: `Ctrl + C`.

## 9. Docker
Перед сборкой: запущен Docker Desktop, в `artifacts/` есть `user_top.json`, `popular.json`, `metrics.json` (Шаг 11 ноутбука).
```powershell
docker build -t recsys-service:1.0 .
docker run --rm -p 8000:8000 --name recsys recsys-service:1.0
```
Проверка (во втором терминале; в Windows `curl.exe`, в Linux/macOS `curl`):
```powershell
curl.exe localhost:8000/health
curl.exe localhost:8000/recommend/172
curl.exe localhost:8000/recommend/999999999     # новый пользователь -> популярные товары
curl.exe localhost:8000/recommend/abc           # ошибка 422
curl.exe localhost:8000/metrics
docker ps                                       # STATUS должен стать (healthy)
```
Экспорт образа для сдачи:
```powershell
docker save -o recsys-service_1.0.tar recsys-service:1.0
```
Запуск на другой машине:
```powershell
docker load -i recsys-service_1.0.tar
docker run --rm -p 8000:8000 recsys-service:1.0
```

**Типичные проблемы**

| Что видите | Причина и решение |
|---|---|
| `FileNotFoundError ... user_top.json` или `COPY failed ... artifacts` | не выполнен Шаг 11, команда запущена не из папки проекта или `artifacts/` исключена в `.dockerignore` |
| `port is already allocated` | порт 8000 занят: запустите с `-p 8001:8000` и обращайтесь на `localhost:8001` |
| `error during connect` / команда `docker` не найдена | не установлен или не запущен Docker Desktop |
| в PowerShell `curl` выводит странное | пишите `curl.exe` |

## 10. Ограничения
- Оценка только по покупателям периода (1131 на validation, 1057 на test): различия меньше ≈0,005 не интерпретируются.
- 81-83% покупателей новые (холодный старт): им рекомендуются популярные товары.
- Нет цены и маржи; метрика оффлайн, эффект на оборот требует A/B-теста.
- Потолок кандидатов "история + 100 популярных" - около 11% покупок validation.
- Рекомендации по истории могут включать товары, которые пользователь уже покупал (вес покупки 15 самый большой); флаг `available` не используется как фильтр, так как он оказался ненадёжным.
- Сервисная модель обучена на всех данных до конца датасета, а метрики посчитаны на test, где модель знала данные только до его начала
- Обучающая таблица XGBoost/FM содержит 324 388 строк, из них 234 положительных (0,07%); при ранней остановке XGBoost выбрал 15 деревьев - данных для сложных моделей мало

## 11. Запуск и воспроизводимость
1. `python -m pip install -r requirements.txt` (библиотеки для ноутбука; для сервиса и Docker - `requirements-service.txt`).
2. Положить `events.csv`, `category_tree.csv`, `item_properties_part1.csv`, `item_properties_part2.csv` в папку `data/` (или рядом с ноутбуком).
3. Выполнить ноутбук: `Restart & Run All`. Результаты сохраняются в `results/`, артефакты сервиса - в `artifacts/`; точные версии библиотек записываются в `requirements-lock.txt`, параметры прогона - в `run_info.json`.
4. Сервис и Docker: разделы 8 и 9.

Время полного прогона ноутбука: 33.3 минуты
